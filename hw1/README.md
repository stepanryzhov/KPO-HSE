# ВышКат

Консольное приложение для учёта парка кикшеринга на Go. Домашнее задание №1 по курсу «Конструирование программного обеспечения».

Транспорт принимается в парк после техосмотра. Приложение учитывает технику и вещи по уникальным инвентарным номерам, рассчитывает суточное энергопотребление и показывает транспорт, подходящий новичкам.

## Запуск

Требуется Go 1.26.5. Сторонних зависимостей нет. Команды выполняются из корня проекта.

```sh
go run ./main
```

При запуске выберите режим в консоли:

- `1` — демонстрация работы с пустым парком, приёма имущества, отказа техосмотра, обработки повторных номеров и некорректных данных.
- `2` — загрузка имущества из JSON-файла. Затем введите путь, например `data/example.json`. Относительный путь отсчитывается от текущей рабочей директории. Путь с пробелами вводится целиком, без кавычек.

В конце обоих режимов выводятся отчёты по количеству объектов, расходу энергии и транспорту для новичков.

## Формат файла

Готовый пример со всеми видами имущества: [data/example.json](data/example.json). Файл содержит JSON-массив объектов, у каждого обязательны `type` и положительный `id`.

| `type` | Данные объекта |
| --- | --- |
| `bicycle` | `gos_number` — госномер, `is_broken` — сломан ли транспорт |
| `scooter` | `gos_number`, `is_broken`, `battery` — заряд от 0 до 100 |
| `electric_bicycle` | `gos_number`, `is_broken`, `battery` — заряд от 0 до 100 |
| `helmet` | `size` — размер шлема |
| `charge_station` | `daily_energy_consumption` — неотрицательный расход в кВт·ч/сутки |

Если дополнительное поле отсутствует, используется нулевое значение: пустой госномер, `false` для `is_broken` и `0` для чисел. Неизвестные поля и типы имущества считаются ошибкой. Пустой массив `[]` создаёт пустой парк.

Ошибки чтения, формата и создания моделей останавливают загрузку до добавления имущества в парк. Каждый объект проходит обычную приёмку: сломанный транспорт и повторные инвентарные номера отклоняются с сообщением в консоли, остальные объекты продолжают загружаться.

| Пакет | Назначение |

| [vehicle](vehicle/) | Модели транспорта |
| [inventory](inventory/) | Модели вещей |

Общие свойства моделей переиспользуются через встраивание структур, а работа с разными видами объектов — через интерфейсы. `Item` объединяет имущество по названию и инвентарному номеру, `IVehicle` описывает транспорт, `IElectroConsumer` — потребителя энергии.

Данные хранятся в памяти. Расход задаётся в кВт·ч/сутки, а транспорт считается подходящим для новичка при простоте использования не ниже 6 из 10.

## SOLID

- **SRP.** Модели отвечают за свои данные, гараж — за учёт, сервис — за техосмотр. Формирование консольного вывода вынесено отдельно.
- **OCP.** Новый вид транспорта можно добавить через реализацию `IVehicle`, не меняя алгоритмы гаража. Для включения в расчёт энергии достаточно реализовать `IElectroConsumer`.
- **LSP.** Все виды транспорта используются через общий контракт `IVehicle`, сохраняя ожидаемое поведение при приёмке и формировании выборок.
- **ISP.** `IVehicle` намеренно объединяет много методов, хотя клиентам нужны не все из них. Это небольшой компромисс с принципом разделения интерфейсов, но для данного проекта единый интерфейс удобен.
- **DIP.** Применён наиболее явно: `Garage` получает `IService` через конструктор, подмена подтверждается тестами.

## DI

[Контейнер в пакете app](app/container.go) создаёт сервис техосмотра и передаёт его гаражу.

`app.New()` собирает приложение с обычным `ServiceCenter`, а `app.NewWithService()` позволяет передать другую реализацию `IService`. Решение о приёмке транспорта определяется результатом этого сервиса.

## Тестирование

```sh
go test ./...
go vet ./...
```

Тесты проверяют валидацию данных, приём имущества, уникальность номеров, расчёт энергии, правило для новичков и чтение файлов. Интеграционные тесты проверяют полный демонстрационный сценарий, остановку при отказе сервиса, выбор режима и загрузку данных через консоль.

- Решение техосмотра проверяет `TestContainerUsesInjectedInspectionDecision` в [app/container_test.go](app/container_test.go). Вместо настоящего сервиса через контейнер передаётся `fakeService` с заданным результатом проверки.
- Правило для новичков проверяет `TestVehiclesForBeginnersUsesInclusiveThreshold` в [garage/garage_test.go](garage/garage_test.go): значение 5 исключается, 6 включается.
- Совместную работу компонентов проверяют тесты в [main/demo_integration_test.go](main/demo_integration_test.go).

## Расширение

**Новый транспорт** реализует существующие интерфейсы и подключается к сценарию. Логику гаража менять не потребуется, пока сохраняются общие правила приёмки и учёта.

**Сотрудники** потребуют отдельной модели и учёта: они не относятся к имуществу и не должны попадать в гараж. Существующие отчёты по парку при этом сохранятся.

**Запчасти** с индивидуальными номерами могут учитываться как вещи через `Item`. Для складских остатков и операций с количеством понадобится отдельный модуль.
